You are building a portable, local-first terminal coding assistant. It is a thin terminal interface around llama.cpp/llama-server and a local coding-oriented GGUF model.

The assistant is generative only:

prompt -> local LLM -> text/code/commands -> user

It does not execute commands, inspect files, modify files, call tools, or operate autonomously.

The user remains the execution boundary. If the model generates a Bash command, Python script, SQL query, configuration change, etc., the user decides whether to inspect, copy, paste, and execute it.

The intended use is day-to-day coding and technical assistance from a terminal, particularly:

Python/pandas/numpy
SQL
R
Bash/Linux administration
Docker
media tooling such as Jellyfin, HandBrake, and MakeMKV
general coding/debugging
generating scripts and commands
explaining technical problems

The project should remain deliberately small. There is no planned agent framework, tool system, sandboxed executor, autonomous loop, or model-controlled filesystem access.

Separated lifecycle management from inference

The command responsibilities are now clearly separated.

ds-start:
Starts and manages llama-server.

ask-ds:
Performs inference only.

ds-status:
Reports state and configuration only.

ds-stop:
Stops the managed llama-server and cleans up runtime state.

This is an important architectural boundary.

ask-ds no longer starts the server automatically.

If the server is unavailable, ask-ds tells the user to run ds-start.

Hardened process ownership

We found and fixed a potentially serious lifecycle problem where ds-stop could theoretically kill an unrelated process if its PID happened to be in the PID file.

ds-stop now verifies the process identity before killing it.

The verification includes:

executable identity
configured model
configured host
configured port
process command line

We explicitly tested this against an unrelated process and confirmed that the unrelated process was not killed.

The model, configuration, scripts, and supporting files now live together in a relocatable bundle.

Removed machine-specific assumptions from the scripts

The scripts now resolve their own actual location rather than assuming a fixed installation directory.

This was necessary because the commands are installed through symlinks in ~/.local/bin.

We found and fixed a real symlink-resolution bug where the scripts incorrectly attempted to find common.sh under ~/.local instead of inside the bundle.

All four scripts now resolve the actual bundle location through readlink -f.

Established the installation model

The user chooses where the bundle lives.

The installer then creates:

~/.local/bin/ask-ds
~/.local/bin/ds-start
~/.local/bin/ds-status
~/.local/bin/ds-stop

as symlinks into that bundle.

The bundle itself is not moved.

The model is not copied.

llama.cpp is not installed by the bundle.

The shell startup files are not modified by the installer.

The server is not started by the installer.

Runtime state is not created by the installer.

This is the intended portable installation model.

Added conservative installer behavior

install.sh validates the bundle and scripts before installing anything.

It:

checks required paths
checks executable bits
checks Bash shebangs
runs bash -n
creates ~/.local/bin if necessary
creates command symlinks
refuses to overwrite unrelated regular files
refuses to overwrite unrelated symlinks
handles symlinks belonging to the current bundle
verifies the resulting links

This has already been exercised against the existing installation.

Established runtime state outside the bundle

Runtime state is kept under:

/tmp/terminal-assistant

Rather than inside the portable bundle.

Current state includes:

llama-server.pid
active-port
llama-server.log

This prevents runtime artifacts from contaminating the portable bundle.

Added alternate-port handling

If the configured port is already occupied by an unrelated service, ds-start does not blindly attempt to start llama-server.

It reports the conflict and asks:

Try a different port? [y/N]

If the user chooses yes, they can provide an alternate port.

The alternate port is intended to be temporary session state and does not modify assistant.env.

Broadened port conflict detection

The original detection relied on an HTTP health endpoint.

That was too narrow because another service could occupy the TCP port without speaking HTTP.

The check now uses ss to detect TCP listeners:

ss -H -ltn "sport = :${PORT}"

This was tested with:

python3 -m http.server 8080 --bind 127.0.0.1

and:

nc -l 8080

Both were correctly detected as port conflicts.

Improved ds-stop cleanup

ds-stop now explicitly removes both:

${PID_FILE}
${ACTIVE_PORT_FILE}

after a successful stop.

That means temporary alternate-port state is explicitly cleaned up rather than relying on a later startup to remove it.

Established the system-prompt direction

The system prompt establishes the assistant as a local terminal coding/technical assistant.

It emphasizes:

direct answers
commands/code first
concise explanations
Astral uv for Python environment/dependency workflows
avoiding pip unless specifically requested or required
not inventing CLI flags/configuration/environment variables
acknowledging uncertainty rather than fabricating tool syntax

This is aligned with the intended generative-only role.

THINGS TO CLEAN UP

Make configured port versus active port explicit

There is a subtle distinction between:

configured port = what assistant.env says

active port = what the current server session actually uses

That distinction should be explicit in common.sh.

For example:

CONFIGURED_PORT=8080
ACTIVE_PORT=8081

rather than relying on PORT being dynamically overwritten.

This prevents stale runtime state from accidentally affecting future startup decisions.

Make alternate-port state completely deterministic

We need to verify:

8080 occupied
-> choose 8081
-> server runs on 8081
-> ds-status reports 8081
-> ask-ds uses 8081
-> ds-stop removes active-port
-> next ds-start returns to 8080

This is an important final test of the new state mechanism.

Handle managed-but-unhealthy state cleanly

There is a meaningful difference between:

no server
our server running and healthy
our server running but unhealthy
another service occupying the port

ds-start and ds-status should distinguish these states rather than collapsing them into "port occupied" or "stopped."

Clean startup failure state

If llama-server fails during startup or exceeds the startup timeout, the PID and active-port state should be cleaned consistently.

Finish stale-PID testing

Test:

stale PID file
PID reused by another process
missing PID file
server already exited
unrelated llama-server
unrelated service using the configured port

The fundamental rule remains:

ds-stop must only stop a process whose identity has been positively verified as belonging to this installation/session.

Test installer relocation

Copy the bundle somewhere else and run install.sh there.

Verify that ~/.local/bin points to the new location.

This is particularly important because portability is one of the project's explicit goals.

Keep the frozen bundle immutable

The frozen known-good bundle should remain untouched.

The workflow should be:

working bundle
-> tests
-> validated
-> new frozen snapshot

rather than modifying the baseline during development.

Decide whether llama.cpp stays an external dependency

For now, llama.cpp is intentionally external.

The bundle owns:

model
configuration
scripts
UX

The machine provides:

llama-server

This is simpler and more portable across hardware than immediately bundling a specific llama.cpp binary.

A bundled llama-server can be reconsidered later if there is a concrete reason.
