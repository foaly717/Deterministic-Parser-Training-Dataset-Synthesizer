1. What I would actually train

For your goal, I would not attempt to "train a model on Bash, UV, and SQL repositories." I would build a domain-specific instruction/SFT corpus around:

Linux shell + Python + SQL + Docker + HandBrakeCLI + MakeMKV + Jellyfin + system administration + documentation-grounded command generation

The training examples should look more like:

USER: How do I list all files larger than 1 GB under /media?

ASSISTANT: find /media -type f -size +1G -print

or

USER: Using only the supplied HandBrakeCLI documentation, what option selects the main feature?
DOCUMENTATION: xyz
ASSISTANT: --main-feature

rather than simply dumping source code into training. The latter teaches behavior rather than merely increasing the model's exposure to code.

and retain source locations.

4. Your own cli_help.py

This is probably only a few hundred lines initially.

Its job is not to understand CLI semantics.

It extracts obvious declarations:

--foo
-f, --foo
--foo <value>
--foo=value

and associates them with their nearby description.

Anything ambiguous gets:

parse_status = "uncertain"

rather than being guessed.

The really important distinction

There are actually two different problems here.

Parsing: Does this text contain --main-feature? Existing tooling + small custom code solves this.
Evidence validation: Is Qwen's answer --main-feature supported by the supplied documentation? That's where your custom code becomes valuable.

You can reduce that to a deterministic set-membership operation:
generated_options <= documented_options
For example:
documented:
    --title
    --preset
    --main-feature
generated:
    --main-feature
→ PASS

versus:
documented:
    --title
    --preset
    --main-feature

generated:
    --main-feature
    --turbo-mode

→ FAIL
That's considerably easier to make reliable than trying to build a general-purpose documentation parser.


Shortcut: For your own training corpus, you don't necessarily need to parse every piece of documentation at all. You can deliberately generate authoritative structured records yourself.
For example:
HandBrakeCLI --help

becomes:
raw help output
       ↓
cli_help parser
       ↓
options.jsonl

Then future Qwen generation operates against options.jsonl. That means your system becomes:
official source
      ↓
deterministic extraction
      ↓
structured evidence
      ↓
Qwen generation
      ↓
deterministic validation
      ↓
training example

The LLM never has to be responsible for extracting the authoritative facts.


I would pin compatible versions rather than blindly installing "latest". There have been compatibility issues between Tree-sitter core and language grammar ABI versions; for example, the Bash grammar has had an incompatibility reported against an older Python Tree-sitter version. Given your preference for reproducible uv environments, I'd put the parser versions directly in pyproject.toml and lock them. 

Don't build parsers from scratch. Build a small evidence/normalization layer around existing parsers:
Tree-sitter ────────┐
SQLGlot ────────────┤
Markdown parser ────┤
Python AST ─────────┤
CLI help extractor ─┤
                    ▼
             your evidence model --> deterministic validator
That is probably 10–20% custom infrastructure rather than 100%, and the custom 10–20% is the part that is actually specific to your terminal-assistant training problem.

Collect source material in its original form.
Parse structured source code deterministically.
Use ASTs to inspect/validate code.
Have separate handling for Python, Bash, SQL, Markdown, etc.
Build preprocessing around the characteristics of each source type.


Suppose your raw dataset contains:
def convert_file(input_path, output_path):
    ...
You could use Tree-sitter to determine:
{
  "language": "python",
  "functions": ["convert_file"],
  "syntax_valid": true
}

But the SFT example should look more like:
{
  "messages": [
    {
      "role": "user",
      "content": "Write a Python function that converts the input file..."
    },
    {
      "role": "assistant",
      "content": "def convert_file(input_path, output_path):\n    ..."
    }
  ]
}

Tree-sitter verifies the generated Python. It doesn't need to become part of what the model sees. 

Where Tree-sitter becomes extremely useful:
Suppose Qwen generates 10,000 Python examples.
Instead of trusting them:
Examples go to Tree-sitter and if they don't parse, discard, if they do parse, become candidates
Then add Python AST, compile, unit tests, and sandbox execution

argparse isn't really a general-purpose parser for arbitrary CLI documentation. It is a Python library for constructing command-line interfaces. If you're trying to determine what options a real program supports from:
HandBrakeCLI --help
argparse doesn't magically parse that output.

You need either: the program's own machine-readable interface, if it provides one; its argument parser/API directly, if you're controlling the program; a purpose-built parser for its help output; or extraction rules appropriate to that particular help format. This is exactly where your small custom --help extractor makes sense.


Next Steps: Deterministic Dataset Validation Blueprint
To avoid scope creep, build a lightweight Python validation package in a clean `uv` environment. The goal of the first experiment is **not** to build a general-purpose documentation parser or training system. It is to establish a reproducible pipeline that can generate candidate SFT examples and reject examples that cannot be supported by the source material.

The key design principle is:
Parsers extract authoritative evidence. Validators check generated examples against that evidence. The parsed AST/evidence is not itself the training representation.

1. Setup Environment & Project Structure
Initialize a clean Python 3.12 workspace:
```bash
uv init terminal_assistant_data
cd terminal_assistant_data
uv add tree-sitter tree-sitter-python tree-sitter-bash sqlglot pytest
```
Use Python's built-in `ast` for Python syntax validation. Use Tree-sitter primarily for structural analysis of Bash/Python source rather than converting source code into AST-based training examples.
Initial structure:

```text
terminal_assistant_data/
├── pyproject.toml
├── src/
│   └── dataset_tools/
│       ├── __init__.py
│       ├── schema.py
│       ├── parsers/
│       │   ├── cli_help.py       # Extract CLI options/evidence
│       │   └── markdown.py       # Extract document structure/code blocks
│       └── validators/
│           ├── schema.py         # Candidate record validation
│           ├── evidence.py       # Validate answers against supplied evidence
│           ├── options.py        # CLI option validation
│           ├── python_ast.py     # Python syntax/AST validation
│           └── sql.py             # SQLGlot syntax/dialect validation
└── tests/
```

Do not build custom Python, Bash, or SQL parsers. Use existing parser libraries and add only the project-specific extraction and validation logic.

2. Define Evidence and Training Schemas
Keep provenance with every extracted fact and generated example so that accepted data can later be traced back to its source.
```python
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class EvidenceFact:
    source_id: str
    source_sha256: str
    tool: Optional[str]
    kind: str
    name: str
    description: Optional[str] = None
    aliases: list[str] = field(default_factory=list)
    parent_command: Optional[str] = None
    line_start: Optional[int] = None
    line_end: Optional[int] = None


@dataclass
class TrainingExample:
    id: str
    instruction: str
    context: Optional[str]
    response: str
    source_sha256: str
    generator_model: str
    status: str = "candidate"
    validation_logs: list[str] = field(default_factory=list)
```

Possible statuses:

```text
candidate
accepted
rejected
needs_review
```

The raw generated candidates should be retained separately from the final accepted SFT dataset.

3. Build Deterministic Evidence Extraction
Start with one concrete source, such as:
```bash
HandBrakeCLI --help
```
The CLI-help parser should extract obvious option declarations such as:

```text
-t, --title <number>
-Z, --preset <string>
--main-feature
```

into structured evidence:

```json
{
  "kind": "option",
  "name": "--main-feature",
  "description": "Detect and select the main feature title."
}
```

The parser should be conservative. If the format is ambiguous, mark the record as uncertain rather than guessing. For Markdown documentation, extract document structure, headings, code blocks, lists, tables, and inline code while retaining source locations.

4. Build Deterministic Validators
The first validator can check whether CLI options appearing in a generated response are present in the extracted evidence. For example:

```python
import re
OPTION_RE = re.compile(r"--?[A-Za-z0-9][A-Za-z0-9-]*")
def validate_cli_response(
    response: str,
    valid_options: set[str],
) -> tuple[bool, str]:
    extracted_flags = set(OPTION_RE.findall(response))

    invalid_flags = extracted_flags - valid_options

    if invalid_flags:
        return False, f"Unsupported options detected: {sorted(invalid_flags)}"

    return True, "All detected options are supported by the supplied evidence."
```

This is intentionally narrow. Option membership does not establish that an argument value is valid; those should be represented separately when the source documents allowed values.

Additional validators should be applied according to the type of example:

```text
Python example → ast.parse() / Tree-sitter
SQL example    → SQLGlot
CLI example    → evidence/options validator
Bash example   → Tree-sitter + safety checks
```

Do not run every validator against every example.

5. Add Candidate Schema Validation and Deduplication
Before semantic validation, verify that Qwen returned a structurally valid training example:

```text
instruction
context
response
```

Reject malformed records before they reach language/tool-specific validators. Also perform deterministic exact deduplication using a normalized hash of the instruction, context, and response.

Keep:

```text
candidates.jsonl
accepted.jsonl
rejected.jsonl
```

separate so that rejection patterns can be analyzed rather than discarded.

6. Generate Candidate Examples with Qwen3-30B-A3B
Use Qwen3-30B-A3B as a synthetic data generator and critic, not as the authority on whether an answer is correct. For Experiment 1, provide the model with a bounded source document/evidence set and ask it to generate candidate instruction/response pairs.
Generate both:
* positive examples where the answer is explicitly supported;
* negative examples where the requested information is absent from the supplied documentation.

For example:

```text
Question:
Using only the supplied documentation, how do I select the main feature?

Expected response:
--main-feature
```

and:

```text
Question:
Using only the supplied documentation, how do I enable turbo encoding?

Expected response:
NOT SPECIFIED IN SUPPLIED DOCUMENTATION.
```

The deterministic evidence layer must independently verify whether the examples actually satisfy those conditions.

7. Execution Workflow for Experiment 1
Start with a small controlled experiment rather than immediately generating thousands of examples:

```text
HandBrakeCLI --help --> deterministic extraction --> structured evidence --> Qwen3-30B-A3B --> ~300 candidate examples --> schema validation --> deduplication --> evidence/tool-specific validation
        │
        ├── accepted
        ├── rejected
        └── needs_review
        │
        ▼
manual inspection/sample audit --> SFT JSONL
```

The initial objective is to measure the quality of the **data-generation and validation pipeline**, not to maximize dataset size.
Track at least:

* candidate count;
* malformed candidate count;
* duplicate count;
* accepted count;
* rejected count;
* rejection reasons;
* manually confirmed false accepts;
* manually confirmed false rejects.

8. Convert Accepted Examples to SFT Format
The model should be trained on normal conversational examples, not Tree-sitter AST representations. For example:

```json
{
  "messages": [
    {
      "role": "user",
      "content": "Using only the supplied documentation, how do I select the main feature?\n\n<documentation>..."
    },
    {
      "role": "assistant",
      "content": "--main-feature"
    }
  ]
}
```

Retain provenance and validation metadata in the master dataset, but omit it from the model-facing SFT representation if the training framework does not require it.
